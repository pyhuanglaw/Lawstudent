# PERF-CAMPUS-DAY-1027（X79）：校園白天走起來會卡——走路途中編 shader（LAWWW2-C 2026-10-27）

- **派工**：LAWWW-C 10-27 18:00 P1（D99：經濟系那一年大多在校園，排在美國單面化前面；量法、做法 LAWWW2 決定）。使用者 X79「校園白天走起來還是會卡（影子閃已修）」。
- **對**：開發 `bbd6a9c7d`（`claude/adoring-meitner-mqzst8`）。
- **環境**：Playwright＋SwiftShader（GPU 也是 CPU 模擬），手機模擬 844×390；另跑一次電腦模式（1280×720，不模擬手機）確認沒有錯誤。SwiftShader 的絕對數字比真機慢很多，只拿來比前後。**沒有在 iPhone、真的電腦上量過。**

## 量法

- `tools/shots/x79_walk.py`：經濟系那一年常走的路線——校門 → 椰林大道 → 總圖 → 社科院 → 霖澤館 → 回椰林大道（遊戲找路的路線，393 步、每步 1.2 m）。11:00、晴天。【捷徑】讀檔；玩家每一格直接往前放 1.2 m（不是搖桿）；路人照常出現、走動。
  逐格記：這一格多久（上一格開始到這一格開始）、render 花多久、這一格新編的 shader（`renderer.info.programs`，記材質名）、新上傳的貼圖、幾何、路人數。有 `Z3.warmup` 的版本先等它做完再走。
- `tools/shots/x79_prof.py`：CPU profiler 開著走第一段（校門 → 椰林大道），把取樣照時間分到每一格，列出最長幾格在做什麼。
- 原始數字的整理：`walk_summary.json`（每一版的新 shader、每格時間分布、新 shader 出現的位置）。

## 找到的原因

- **第一次走**：路上 30 個新 shader。扣掉剛起步那幾格（站在校門口時畫面裡已經有的），走路途中還有 13 次「這一格編新的 shader」，每次停 0.5～2.2 秒：

  | 位置 | 新編的 shader | 那一格 render |
  |---|---|---|
  | 校門往東 10 m | 陰影的深度 shader ×5（新的投影子物件走進陰影範圍） | 1.6 秒 |
  | 校門往東 14 m | 路人「遠距離版本」的 toon（第一個路人走到 18 m 外） | 2.2 秒 |
  | 總圖東側 | 陰影的深度 shader | 0.5 秒 |
  | 社科院門口 | 社科院門廊的金色、天花板、屋頂（第一次進畫面） | 0.6～0.7 秒 |
  | 往霖澤館途中 | 陰影的深度 shader | 1.1 秒 |

- **第二次走同一條路**：新 shader 0 個，最慢一格 1.19 秒（校門口人最多的地方，11 個路人、580 draw call）——「走起來卡一下」是第一次看到才編造成的。
- three.js 第一次畫到一個材質才編它的 shader。既有的 `Z3.prewarm`（PERF-ZONE-ENTER-1018）只在電腦上、只在剛進區域的黑畫面做、只編那時候已經接上的物件；之後才接上的正式模型、藏著的遠距離版本、還沒生出來的路人、陰影那一輪都沒編；手機完全不做。
- **只「送出」編譯還不夠**（第二版量到的）：three.js 第一次畫到時會讀編譯結果（`onFirstUse` → `getProgramInfoLog`），那時候 GPU 還沒編完就要等——第二版路上新 shader 0 個，起點附近仍有 4 格 1～2.5 秒全花在 `getProgramInfoLog`。

## 修法：`Z3.warmup`（`src/zones3d.js`）＋`GAME.enter` 一行（`src/game3d.js`）

淡入以後在背景每 0.25 秒做一小批：

1. 場景裡看得到（visible，不管在不在畫面裡）而沒編過的材質：`renderer.compile(物件, 鏡頭, E.scene)`——燈光、霧照區域的，編出來的就是畫的時候要用的那一個。藏起來的不編（被正式模型取代的套件備用模型）；material 不是真材質的（溫州街的 TK paint 描述）不碰；子樹裡有燈的不編（compile 會把那盞燈多算一次）。
2. 還沒放進場景的路人底模（`ASSETS.cache` 裡的 VRM 樣板：等一下才生出來的人用的就是它的材質）、遠距離版本的 toon 材質（用 SkinnedMesh 編，和遊戲裡一樣）也編。
3. 編好的 shader 主動讀一次（`program.getUniforms()`＝第一次畫到時的 `onFirstUse`），等 GPU 的時間發生在剛進場站著的時候。
4. 場景裡都編完、連續幾次沒有新的以後，陰影相機暫時放大到整個區域畫一格，陰影的深度 shader 一次編完；畫完相機還原、下一格重畫陰影（**那一格的影子比較糊，只有一次**）。
5. 做完以後每 3 秒再看一次（之後才載完的路人底模、正式模型），有就照樣編；換區域就停。
6. 一批的量：有平行編譯（`KHR_parallel_shader_compile`）最多 8 個新的 shader、只讀已經好的（不會等）；沒有的一批 1 個。
7. 電腦另外把這些物件的貼圖先傳上 GPU（每批約 400 萬像素；VRM 的 MToon 貼圖在 uniforms 裡也傳）；**手機貼圖照舊第一次畫到才傳**（顯示記憶體）。
8. 網址 `?nowarmup` 關掉（比較用）；`E.lastWarmup` 記結果。

## 改前改後（同一條路線第一次走；SwiftShader 手機模擬）

| | 改前 | 第一版（只編場景裡的） | 第二版（＋路人底模、遠距離版本） | **第三版（交件：＋主動讀一次）** |
|---|---|---|---|---|
| 走路途中新編的 shader | 30 | 4 | 0 | **0** |
| 超過 1 秒的格子 | 9 | 4 | 7 | **3** |
| 卡頓多出來的時間合計（超過中位數 2 倍的格子） | 9.5 秒 | 5.8 秒 | 8.5 秒 | **3.9 秒** |
| 每格第 99 百分位 | 1.60 秒 | 1.47 秒 | 1.34 秒 | **0.98 秒** |
| 每格中位數 | 0.50 秒 | 0.49 秒 | 0.49 秒 | 0.48 秒 |

- 第三版剩下的 3 格：兩格在剛起步、第一次轉向東邊時一次上傳 81～127 張貼圖（手機照舊第一次看到才傳）；一格是 GPU 忙（主執行緒閒著）。
- **平均每格的時間沒變**（中位數 0.48～0.50 秒）：這一份只處理「第一次走卡一下」，人多的校門口、椰林大道（draw call 500 以上）平常就慢的部分沒動。

## 代價

- 等待挪到剛進場、站著的時候：SwiftShader 手機模擬 61 秒做完（期間 13 格超過 1 秒）；電腦模式 83 秒（多先傳了 467 張、71.8 百萬像素的貼圖）。真機的 shader 編譯是幾毫秒到幾十毫秒，**沒有量過**。玩家在做完之前就開始走，沒編到的照舊第一次畫到才編（不會比原本差）。
