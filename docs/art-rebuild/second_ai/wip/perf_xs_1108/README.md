# 新生南路山嵐、大口效能（BB-B PERF1108_9526，P3、不擋）：先量再改（LAWWW2-B 2026-11-08）

**狀態：量測腳本交 CC**。我這邊沒有瀏覽器、沒有 GPU（D131），不能自己量；猜錯就會改錯地方，所以先請 CC 在 PC 上做對照測量。

## BB-B 量到的（AMD RX 6600M，線上 v9.10.23，?perf、14:00 晴、medium）
- 山嵐 32.1 fps／1% low 4.7／95 calls；大口 35.8／6.5／130（最慢一幀 433 ms）。

## 請 CC 跑：`perf_ab_probe.js`
- 進區域、站好以後，在 DevTools console 貼上，或用 Playwright 跑 `page.evaluate`。約 60 秒。
- 量哪幾個點：
  - 山嵐：一樓門口往裡看，加上二樓；
  - 大口：一樓、二樓各一個點；
  - 好拍：對照組；
  - 同弦：只看卡頓那一段。
- 對照怎麼量：每一種情況先等 2 秒，再量 5 秒的平均 fps、最慢一幀。
  - 情況：照舊／關光暈／關半透明／關 PointLight／關二樓／太陽不投影／解析度減半。
  - 一次只關一樣，量完復原。
  - 最後再量一次照舊，看前後有沒有飄。
- 卡頓怎麼記：站 20 秒，每一個超過 100 ms 的幀，記下那一幀 shader 程式數、貼圖數、幾何數、NPC 數有沒有變。

## 怎麼讀結果、接下來改什麼
- 解析度減半就快很多，表示瓶頸是每個像素的成本。再看關哪一樣恢復最多：
  - 關光暈恢復最多：光暈縮小、減少數量，或改成不透明的發光面（山嵐有 74 個）；
  - 關半透明恢復最多：玻璃改成不透明的窗景，或背面剔除、只畫一面；
  - 關二樓恢復最多：看不到的那一層不畫，比照 E.shadowLevels，只畫玩家那一層加上看得到的挑空。
- 解析度減半也沒變快：瓶頸在 CPU 或陰影，再看關太陽投影那一項。
- 卡頓那幾幀如果 shader 程式數有增加：那一下在編 shader，用 E.pinPrograms 預先編好、進區域時先編。
- 卡頓那幾幀如果 NPC 數有變：有人走進來，同 PERF-COLD 的預先載入。

## 第 2 版（11-08 19:5x，看了第一次參考數據以後）
- 第一次（PERFAB_8172）是和其他測試同時跑的，只當參考。可以看出兩件事：
  - **解析度減半沒變快**：不是 GPU 填像素的問題，比較像 CPU。
  - **山嵐 2F 有 3 幀卡 260～290 ms**：卡的當下 shader、貼圖、幾何、NPC 數都沒變。
- 懷疑一：NPC 找路。`path_bench.js`（這個資料夾）在 Node 建出遊戲真正的區域，隨機起訖點各 60 次。

| 店 | 導航格（0.1 m） | 同一層找一次 平均／最慢 | 跨層 平均／最慢 |
|---|---|---|---|
| 好拍（1 層） | 64×160 | 0.6／9.5 ms | — |
| 山嵐（2 層） | 160×200 ×2 | 2.2／29.5 ms | **13.8／48.2 ms** |
| 大口（2 層） | 140×180 ×2 | 1.3／14.0 ms | 7.5／25.9 ms |

  - 單次找路解釋不了 270 ms。但好幾個 NPC 同一幀找路（例如整點換作息），就會疊起來。
- 懷疑二：NPC 本身（動畫、彈簧骨）。兩間座位多（大口 79、山嵐 16＋坐地板 10），NPC 多。
- 所以 `perf_ab_probe.js` 第 2 版：
  - 多一項 `noNPC`；
  - 每一種情況多記每幀 `E.render` 的時間（畫面）、`E.pathTo` 的次數和時間（找路）；
  - 卡頓表每一幀也記這兩樣。
- 怎麼讀：
  - 卡頓那幀 `pathMs` 很大：找路。改法是 NPC 找路分散到不同幀（一幀最多找一次），或兩層的店導航格改 0.2 m。這屬於 LAWWW-B 的引擎和 NPC 那一塊，我會附 patch。
  - `noNPC` 恢復最多：NPC 數量或動畫。
  - `renderMs` 佔了大部分：畫面，回到上面的光暈、半透明、二樓。

## 第 2 版結果（PERFAB_8172v2：SOLO、每個點先站 30 秒；CC-B 20:41）與結論
| 點 | NPC | base fps／畫面 ms | noNPC | noPoint | noBlend | noL2 | halfRes | base2 |
|---|---|---|---|---|---|---|---|---|
| 山嵐 1F | 9 | 39.7／9.3 | **57.9** | 57.4 | 50.9 | 51.3 | 55.3 | 56.6 |
| 山嵐 2F | 9 | 33.2／12.6 | **57.8／7.1** | 53.6 | 44.0 | 48.7 | 36.2 | 38.0 |
| 大口 1F | 9～11 | 54.5～58.4（每一種都差不多） | | | | | | |
| 大口 2F | 9～11 | 45.1／12.7 | **57.2／8.2** | 40.1 | 44.1 | 37.0 | 35.8 | 36.7 |
| 好拍、同弦 | 1～2 | 57～60（全部） | | | | | | |

- **主因是 NPC**：三個慢的點都是一拿掉 NPC（6～11 個）就回到 57～58，每幀畫面時間 12～15 → 7～8 ms。好拍、同弦 NPC 只有 1～2 個。
  - 這是人物系統：同一間店裡同時幾個 NPC、坐著的 NPC 用什麼模型、多久更新一次。屬 LAWWW-B。
  - 可以考慮的方向：
    1. 室內店家同時在場的 NPC 上限；
    2. 坐著不動的 NPC 用博思 101 那套替身遠近（seated_figures_lod）；
    3. 坐著、在畫面外的 NPC 動畫和彈簧骨降頻更新。
- **排除**：
  - 找路：每幀 < 0.2 ms；
  - 二樓時一樓也在畫：大口 2F 藏一樓 37.4，前後 32.8、38.3，沒差；
  - GPU 填像素：解析度減半不變快。
- **待確認**：山嵐關 PointLight 兩個點都回升（57.4、53.6），大口沒有。可能是燈多、每個人物材質的成本跟著放大。NPC 處理完再量一次。
- **小卡頓（100～120 ms）**：那一幀畫面只有 7～11 ms，沒有任何計數改變，是畫面以外的 JavaScript（或垃圾回收）。這次的欄位分不出是什麼，要錄 CPU 效能紀錄（DevTools Performance／CDP Tracing）20 秒才看得到是哪個函式。
